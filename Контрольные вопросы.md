## 1. HTTP-методы и CRUD

> **Коротко:** CRUD — четыре операции над данными (создать, прочитать, обновить, удалить). В HTTP им соответствуют методы POST, GET, PUT/PATCH, DELETE.

### Соответствие CRUD и HTTP

| CRUD | Метод | Пример в нашей лабе | Что делает |
|---|---|---|---|
| **C**reate | `POST` | `POST /cars` | создаёт новую запись, `id` выдаёт сервер |
| **R**ead | `GET` | `GET /cars`, `GET /cars/3` | читает, ничего не меняет |
| **U**pdate (целиком) | `PUT` | `PUT /cars/3` | заменяет запись полностью |
| **U**pdate (частично) | `PATCH` | `PATCH /cars/3` | меняет только присланные поля |
| **D**elete | `DELETE` | `DELETE /cars/3` | удаляет запись |

### Безопасные и идемпотентные методы

- **Безопасный метод** — не меняет данные на сервере. Его можно вызывать сколько угодно, ничего не сломается (браузер и поисковики часто делают GET сами).
- **Идемпотентный метод** — повторный вызов даёт **то же состояние сервера**, что и один вызов.

| Метод | Безопасный | Идемпотентный | Почему |
|---|:---:|:---:|---|
| `GET` | да | да | только читает |
| `HEAD` | да | да | как GET, но без тела ответа |
| `OPTIONS` | да | да | спрашивает, какие методы разрешены |
| `PUT` | нет | **да** | повторная замена теми же данными даёт тот же результат |
| `DELETE` | нет | **да** | после первого удаления запись уже нет, дальше ничего не меняется |
| `POST` | нет | **нет** | каждый вызов создаёт новую запись |
| `PATCH` | нет | не гарантирован | зависит от того, что именно делает патч (см. раздел 8) |

**Пример с нашим сервисом:**

```
POST /cars  (тот же JSON два раза)   -> появилось ДВЕ машины (id 6 и 7)       -> не идемпотентен
PUT  /cars/3 (тот же JSON два раза)  -> машина 3 перезаписана, итог тот же    -> идемпотентен
DELETE /cars/3 два раза              -> 1-й раз 200, 2-й раз 404, но в базе
                                        состояние одинаковое (машины 3 нет)   -> идемпотентен
```

Важно: идемпотентность смотрят по **состоянию сервера**, а не по коду ответа. Поэтому DELETE идемпотентен, хотя второй ответ 404.

### Коды ответов, которые стоит знать

| Код | Значение | Где у нас |
|---|---|---|
| 200 | OK | успешный GET, PUT, PATCH, DELETE |
| 201 | Created | успешный POST |
| 204 | No Content | успех без тела (у нас не используется) |
| 400 | Bad Request | кривой запрос |
| 404 | Not Found | нет машины с таким id |
| 422 | Unprocessable Entity | pydantic отклонил данные (`price: -5`, `sort_by=abc`) |
| 500 | Internal Server Error | ошибка на стороне сервера |

## 2. RESTful архитектура

> **Коротко:** REST — стиль построения API, где всё это **ресурсы** с адресами (URI), а действия над ними выражаются методами HTTP, и сервер не хранит состояние между запросами (stateless).

REST предложил Рой Филдинг в диссертации в 2000 году. Это набор ограничений, а не готовый протокол.

### Принципы REST

| Принцип | Смысл |
|---|---|
| **Клиент-сервер** | клиент и сервер разделены и развиваются независимо |
| **Stateless** (без состояния) | каждый запрос содержит всё нужное, сервер не помнит предыдущие |
| **Кэшируемость** | ответы помечаются, можно ли их кэшировать |
| **Единый интерфейс** | одинаковые правила для всех ресурсов (методы, URI, форматы) |
| **Слоистая система** | между клиентом и сервером могут быть прокси, балансировщики (как Cloudflare перед Render) |
| **Код по требованию** (необязательный) | сервер может отдавать клиенту исполняемый код, например JS |

### Ресурсы и URI

Ресурс — это **существительное** (сущность), а не действие. Действие задаёт метод HTTP.

| Плохо (действие в адресе) | Хорошо (ресурс + метод) |
|---|---|
| `GET /getCars` | `GET /cars` |
| `POST /createCar` | `POST /cars` |
| `POST /deleteCar?id=3` | `DELETE /cars/3` |
| `/car/3/update` | `PUT /cars/3` |

Правила хорошего URI: существительные во множественном числе (`/cars`), иерархия для вложенных ресурсов (`/cars/3/owners`), фильтры и сортировка в query (`/cars?sort_by=price`).

### Что значит stateless

```
Stateful (с состоянием):                Stateless (REST):
Клиент: "залогиниться"                  Клиент: GET /cars/3 + токен
Сервер: запомнил сессию                 Сервер: проверил токен, ответил, забыл
Клиент: "дай мою корзину"               Клиент: GET /cart + токен
Сервер: достал из памяти сессию         (любой экземпляр сервера может ответить)
```

Плюс: можно запустить много копий сервера за балансировщиком, любая обработает любой запрос. База данных при этом не нарушает stateless: данные ресурсов хранятся, но **сессия клиента** на сервере не держится.

### Где наш сервис по уровням REST (модель Ричардсона)

| Уровень | Что это | У нас |
|---|---|---|
| 0 | один URL, всё через POST | нет |
| 1 | отдельные ресурсы с адресами | да (`/cars`, `/cars/3`) |
| 2 | правильные методы HTTP и коды ответа | да |
| 3 | HATEOAS: в ответе ссылки на следующие действия | нет |

Итого наш API на уровне 2, что для большинства практических REST API нормально.

## 3. JSON-RPC и XML-RPC

> **Коротко:** RPC (Remote Procedure Call) — удалённый вызов процедуры: клиент вызывает функцию на сервере, как будто она локальная. JSON-RPC и XML-RPC — две реализации, отличаются формат данных (JSON или XML).

### Идея RPC против REST

| | REST | RPC |
|---|---|---|
| Центр API | **ресурс** (`/cars/3`) | **функция** (`getCar(3)`) |
| Адрес | много URL | обычно один URL (endpoint) |
| Метод HTTP | разный (GET, PUT...) | как правило, всегда POST |
| Мысль | «дай ресурс» | «вызови действие» |

### XML-RPC (1998)

- Запрос и ответ в **XML**, передаются по HTTP POST.
- Простой, но многословный.

```xml
<methodCall>
  <methodName>getCar</methodName>
  <params><param><value><int>3</int></value></param></params>
</methodCall>
```

### JSON-RPC (версия 2.0)

- Тот же принцип, но формат **JSON**, поэтому компактнее и удобнее.
- Запрос содержит версию, имя метода, параметры и `id` (чтобы сопоставить ответ с запросом).

```json
-> {"jsonrpc": "2.0", "method": "getCar", "params": {"id": 3}, "id": 1}
<- {"jsonrpc": "2.0", "result": {"brand": "BMW", "price": 5200000}, "id": 1}
<- {"jsonrpc": "2.0", "error": {"code": -32601, "message": "Method not found"}, "id": 1}
```

Особенности JSON-RPC: **уведомления** (запрос без `id`, ответа не ждём), **пакеты** (несколько вызовов в одном массиве).

### Отличия

| | XML-RPC | JSON-RPC |
|---|---|---|
| Формат | XML | JSON |
| Размер | больше | меньше |
| Типы данных | фиксированный набор тегов | типы JSON |
| Пакеты и уведомления | нет | да (в версии 2.0) |
| Транспорт | HTTP | HTTP, WebSocket, TCP и др. |

Родственник: **SOAP**, тоже XML и RPC-подход, но намного тяжелее (схемы WSDL, конверты).

## 4. gRPC

> **Коротко:** gRPC — быстрый RPC-фреймворк от Google. Данные передаются в бинарном формате **Protobuf** поверх **HTTP/2**, поддерживается потоковая передача (streaming).

### Из чего состоит

1. **Protobuf** (Protocol Buffers) — бинарный формат сериализации. Структуры описываются в файле `.proto`, потом по нему генерируется код для любого языка.
2. **HTTP/2** — транспорт (мультиплексирование, один канал для множества запросов).
3. **Кодогенерация** — клиент и сервер получают готовые классы и методы.

```proto
syntax = "proto3";

message Car {
  int32  id    = 1;
  string brand = 2;
  double price = 3;
}

service CarService {
  rpc GetCar (GetCarRequest) returns (Car);          // обычный вызов
  rpc ListCars (Empty) returns (stream Car);         // сервер отправляет поток
}
```

### Четыре типа вызовов (streaming)

| Тип | Как это выглядит |
|---|---|
| **Unary** | один запрос, один ответ (как обычный REST) |
| **Server streaming** | один запрос, сервер шлёт поток ответов |
| **Client streaming** | клиент шлёт поток, в конце один ответ |
| **Bidirectional** | оба шлют потоки одновременно (чат, телеметрия) |

### gRPC против REST

| | REST + JSON | gRPC |
|---|---|---|
| Формат | текст (JSON) | бинарный (Protobuf) |
| Скорость и размер | медленнее и больше | быстрее и компактнее |
| Контракт | OpenAPI (необязательный) | `.proto` (обязательный) |
| Браузер | работает напрямую | нужен прокси (gRPC-Web) |
| Отладка | легко читать руками | бинарь, нужны инструменты |

Где применяют: связь микросервисов внутри компании, мобильные приложения, потоковые данные.

## 5. CORBA и DCOM

> **Коротко:** старые технологии распределённых объектов 90-х. Позволяли вызывать методы объектов на другой машине. Устарели из-за сложности и проблем с сетью и совместимостью, их вытеснили веб-сервисы, REST и gRPC.

| | CORBA | DCOM |
|---|---|---|
| Кто создал | консорциум OMG (1991) | Microsoft (1996) |
| Платформа | кроссплатформенная, много языков | в основном Windows |
| Как работает | посредник **ORB**, интерфейсы на языке **IDL**, протокол IIOP | расширение COM на сеть, основано на DCE/RPC |

### Почему устарели

- **Сложность:** тяжёлые спецификации, трудно разрабатывать и отлаживать.
- **Сеть и файрволы:** динамические порты, сложно пропустить через межсетевой экран, в отличие от обычного HTTP на порту 80/443.
- **Несовместимость:** у разных производителей реализации отличались.
- **Привязка:** DCOM только к Windows и бинарному COM.
- **Безопасность:** слабая и сложная в настройке.
- Интернет пошёл по простому пути (HTTP + JSON/XML), а не по тяжёлому «распределённые объекты».

### Чем заменили

| Было | Стало |
|---|---|
| CORBA | SOAP, REST, gRPC, брокеры сообщений (Kafka, RabbitMQ) |
| DCOM | .NET Remoting, затем WCF, затем gRPC и REST |

## 6. Виды документации API

> **Коротко:** документация описывает, какие у API есть эндпоинты, параметры и ответы. Основной стандарт — OpenAPI (Swagger), есть альтернативы RAML и API Blueprint, а Postman используют для тестирования и документирования коллекций запросов.

| Инструмент | Что это | Формат | Особенность |
|---|---|---|---|
| **OpenAPI / Swagger** | стандарт описания REST API | YAML или JSON | самый распространённый, есть Swagger UI и кодогенерация |
| **RAML** | язык моделирования REST API | YAML | упор на «сначала дизайн», повторное использование частей |
| **API Blueprint** | описание API | Markdown | удобно читать как обычный текст |
| **Postman** | приложение для работы с API | коллекции | запросы, тесты, моки, генерация документации |

### Swagger и OpenAPI: что есть что

Swagger — старое название спецификации. В 2015 её передали в Linux Foundation, и она стала **OpenAPI Specification**. Теперь «Swagger» чаще означает набор **инструментов** (Swagger UI, Swagger Editor), а «OpenAPI» — сам стандарт.

Версии: Swagger 2.0 → OpenAPI 3.0 → 3.1.

### Два подхода

| | Code-first | Design-first |
|---|---|---|
| Идея | сначала пишем код, документация из него | сначала описываем API, потом код |
| Пример | **FastAPI** (наша лаба): `/docs` строится из типов и моделей | пишем `openapi.yaml`, потом реализуем |
| Плюс | документация не расходится с кодом | контракт согласован до разработки |

В нашей лабе: FastAPI генерирует `/openapi.json` сам, Swagger UI на `/docs` рисует по нему интерфейс. Во Flask (flasgger) YAML приходится писать руками в docstring.

## 7. Заголовки HTTP: Host, Referer, Range

> **Коротко:** `Host` указывает, к какому сайту обращаемся, `Referer` показывает, откуда пришёл запрос, `Range` запрашивает часть ресурса.

### Host

- **Назначение:** на какой домен (и порт) адресован запрос. Обязателен в HTTP/1.1.
- **Зачем:** на одном IP-адресе может жить много сайтов (виртуальный хостинг), сервер по `Host` выбирает нужный.

```
GET /cars HTTP/1.1
Host: web-services-lab4.onrender.com
```

- **Безопасность:** *Host header injection*. Если приложение строит ссылки (например, для сброса пароля) из `Host` без проверки, злоумышленник подменяет заголовок и ссылка уходит на его сайт. Защита: сверять `Host` с белым списком разрешённых доменов.

### Referer

- **Назначение:** адрес страницы, с которой пришёл запрос (с какой ссылки перешли).
- **Забавный факт:** в слове ошибка (`Referer` вместо `Referrer`) попала в стандарт ещё в 90-х и осталась.

```
Referer: https://example.com/search?q=bmw
```

- **Применение:** аналитика (откуда трафик), защита от «хотлинка» картинок, дополнительная проверка против CSRF.
- **Безопасность:** утечка приватности. Если в URL предыдущей страницы был токен или персональные данные, они уйдут на другой сайт. Регулируется заголовком `Referrer-Policy`. Заголовок легко подделать, поэтому как единственную защиту использовать нельзя.

### Range

- **Назначение:** запросить только **часть** ресурса.

```
GET /video.mp4 HTTP/1.1
Range: bytes=0-499          <- хочу первые 500 байт

HTTP/1.1 206 Partial Content
Content-Range: bytes 0-499/10000
Accept-Ranges: bytes
```

| Что | Значение |
|---|---|
| `206 Partial Content` | отдана часть |
| `Content-Range` | какой кусок и общий размер |
| `Accept-Ranges: bytes` | сервер умеет отдавать части |
| `416 Range Not Satisfiable` | запрошен диапазон за пределами файла |

- **Применение:** перемотка видео, докачка файлов после обрыва, параллельная загрузка кусками.
- **Безопасность:** Range-атака на отказ в обслуживании. Запрос с множеством перекрывающихся диапазонов заставляет сервер тратить много ресурсов (известный случай: *Apache Killer*, 2011).

### Сводка

| Заголовок | Кто шлёт | Для чего | Главный риск |
|---|---|---|---|
| Host | клиент | выбрать сайт на сервере | подмена Host (injection) |
| Referer | клиент (браузер) | откуда пришли | утечка URL |
| Range | клиент | получить часть ресурса | перегрузка сервера |

## 8. PUT, PATCH и идемпотентность

> **Коротко:** `PUT` **заменяет** ресурс целиком, `PATCH` **меняет часть** полей. PUT всегда идемпотентен, PATCH только если сам патч идемпотентен.

### Разница

Допустим, в базе машина 3: `{brand: BMW, model: X5, color: white, year: 2020, price: 5200000, mileage: 40000, power: 249}`.

| | PUT | PATCH |
|---|---|---|
| Что присылаем | **все** поля | **только** изменяемые |
| Что делает | полная замена | частичное изменение |
| Пример тела | весь объект с новой ценой | `{"price": 4900000}` |
| Если забыть поле | ошибка (у нас 422) | остальные поля не трогаются |

В нашей лабе реализованы `PUT` и `PATCH`. Для `PUT` клиент присылает все поля, а для `PATCH /cars/3` достаточно, например, `{"price": 4900000}`. В ответ приходит полный объект машины. Пустой объект `{}` ничего не меняет; поля со значением `null` пропускаются. Неизвестные поля и попытка изменить `id` дают 422. Если машины нет — 404.

### Идемпотентность

Повторный вызов с теми же данными не меняет результат после первого.

| Пример | Идемпотентно? | Почему |
|---|:---:|---|
| `PUT /cars/3` с телом `{...price: 900000}` | да | сколько ни повторяй, цена 900000 |
| `PATCH` с `{"price": 900000}` | да | результат тот же |
| `PATCH` «увеличить цену на 1000» | **нет** | каждый вызов добавляет ещё 1000 |
| `POST /cars` | нет | каждый вызов создаёт новую машину |
| `DELETE /cars/3` | да | после первого раза машины нет, дальше ничего не меняется |

### Зачем это нужно

Сеть ненадёжна: запрос мог не дойти или ответ потерялся. Клиент повторяет запрос. Если метод идемпотентен, повтор безопасен. Если нет (как POST), можно случайно создать дубликат, например заказ дважды. Поэтому для платежей и заказов вводят специальные ключи идемпотентности.

## 9. HTTP/2 против HTTP/1.1

> **Коротко:** HTTP/2 передаёт данные бинарными кадрами, умеет **мультиплексирование** (много запросов в одном соединении одновременно), **сжимает заголовки** (HPACK) и имел функцию server push.

### Проблема HTTP/1.1

```
HTTP/1.1: запросы по очереди в одном соединении, ответ 2 ждёт, пока придёт ответ 1.
Браузер обходит это, открывая 6 параллельных соединений.

Соединение 1: [запрос A]-----[ответ A]  [запрос B]-----[ответ B]
```

### Что принёс HTTP/2

| Возможность | Суть |
|---|---|
| **Мультиплексирование** | много запросов и ответов идут **одновременно** по одному TCP-соединению (каждый в своём «потоке») |
| **Сжатие заголовков (HPACK)** | заголовки повторяются в каждом запросе (Host, cookie и т.д.), HTTP/2 сжимает их и не шлёт повторно то, что уже отправлено |
| **Server push** | сервер мог отправить файлы (CSS, JS) заранее, пока клиент их не запросил |
| **Бинарный протокол** | вместо текста кадры (frames), быстрее разбирать |
| **Приоритеты потоков** | можно указать, что важнее загрузить первым |

```
HTTP/2: один TCP-канал, много потоков параллельно

Поток 1: ====A====
Поток 2:   ==B==
Поток 3:       ======C======
```

### Сравнение

| | HTTP/1.1 | HTTP/2 |
|---|---|---|
| Формат | текстовый | бинарный |
| Параллельность | несколько соединений | мультиплексирование в одном |
| Заголовки | текст, повторяются | сжимаются (HPACK) |
| Server push | нет | есть (в браузерах почти не используется, Chrome отключил в 2022) |
| TLS | не обязателен | в браузерах де-факто только с TLS |

### Что дальше: HTTP/3

У HTTP/2 остаётся проблема на уровне TCP: потеря одного пакета тормозит все потоки. HTTP/3 работает поверх **QUIC** (на UDP) и решает её.

### Связь с нашей лабой

В заголовках ответа Render мы видели `alt-svc: h3=":443"`, то есть сервер предлагает перейти на HTTP/3, а `x-firefox-http3: h3` показывал, что браузер реально так и сходил. Сам `uvicorn` в нашем проекте говорит по HTTP/1.1; современные протоколы на себя берёт Cloudflare перед Render.

## 10. Шпаргалка одной фразой

| Вопрос | Ответ |
|---|---|
| CRUD и HTTP | Create=POST, Read=GET, Update=PUT/PATCH, Delete=DELETE |
| Безопасный метод | не меняет данные на сервере (GET, HEAD, OPTIONS) |
| Идемпотентный метод | повтор даёт то же состояние (GET, PUT, DELETE; не POST) |
| REST | ресурсы с URI + методы HTTP + stateless |
| Stateless | сервер не хранит сессию клиента, каждый запрос самодостаточен |
| URI в REST | существительные во множественном числе: `/cars/3` |
| RPC против REST | RPC вызывает функции, REST оперирует ресурсами |
| XML-RPC / JSON-RPC | удалённый вызов функций поверх HTTP в XML или JSON |
| gRPC | RPC от Google: Protobuf + HTTP/2 + streaming |
| CORBA, DCOM | старые распределённые объекты, устарели из-за сложности и проблем с сетью |
| OpenAPI / Swagger | стандарт описания REST API в YAML/JSON, Swagger UI для просмотра |
| RAML / Blueprint | альтернативы описания API (YAML / Markdown) |
| Postman | инструмент для запросов, тестов и документации коллекций |
| Host | какой сайт запрашиваем; риск: Host injection |
| Referer | откуда пришёл запрос; риск: утечка URL |
| Range | запрос части ресурса (ответ 206); риск: DoS множеством диапазонов |
| PUT против PATCH | PUT заменяет целиком, PATCH меняет часть |
| Идемпотентность | много вызовов = один по результату |
| HTTP/2 | мультиплексирование + HPACK + бинарный формат (+ server push) |

### Вопросы, которые могут задать «по нашему коду»

- **Чем отличаются ваши PUT и PATCH?** PUT требует все поля автомобиля, PATCH обновляет только переданные. Наш PATCH присваивает значения, поэтому повтор одинакового запроса не меняет результат — он идемпотентен.
- **Почему `/cars/stats` стоит выше `/cars/{car_id}`?** FastAPI ищет маршруты сверху вниз, иначе слово `stats` попало бы в `car_id`.
- **Откуда Swagger знает про эндпоинты?** FastAPI сам строит `/openapi.json` из декораторов, типов аргументов и pydantic-моделей.
- **Ваш API stateless?** Да, сервер не хранит сессий; состояние только в данных (в базе).
